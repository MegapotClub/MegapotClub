# Architecture and invariants

Megapot Club is a static React application using wagmi, RainbowKit, viem and TanStack Query. Build-time rendering produces nine HTML entrypoints for eight languages. Relative assets and fragment routes work under IPFS path prefixes. Preferences and transaction journals stay in the browser; external RPC and indexed services provide public observations.

Queries isolate account, draw and endpoint configuration. Unknown amounts never become zero. A failed refresh may retain the same account's last valid observation. ENS identities share the wallet/query cache. Home and Results share the five largest wallet/draw win totals in a fourteen-day window. Indexed data enriches display and never authorizes signing.

Disconnected startup performs the shared draw observation and batched ENS lookup, with no account or journal-recovery reads. RPC defaults are normalized before query keys are created. Winner queries wait for the round-list request to finish, retaining the cached presentation meanwhile. Transaction recovery uses one stable, cancellable query for the active account and configured endpoints, processing one attempt per interval. Old attempts back off to five minutes; recent hashless attempts to one minute. A healthy RPC returning a missing receipt remains pending and does not trigger failover. Candidate verification remains exact and never sends a transaction. Disconnect pauses restored recovery while preserving every journal record; responses to already-submitted wallet requests remain independently observed.

`native.ts` owns literal typed ABIs and canonical actions. Retail reviews read sale flags, wallet funds, allowance and relevant ticket state at a consistent fresh block; they do not fetch unrelated LP/helper positions. Suitable calls use multicall. Simulation preserves the actual sender. Positive immutable runtime checks are cached by endpoint/address/hash for ten minutes. Every signature request still gets fresh state, simulation and provider/account/chain verification.

`purchaseDraft.ts` preserves selections and a unique journey/revision. Explicit valid invitations take precedence over `CLUB_REFERRER` in `referral.ts`; invalid invitations require an explicit clear. The immutable order retains that single beneficiary with weight 1e18, recipient, numbers and quantity. The source tag is separate from attribution. When allowance is insufficient, approval is for the exact total and purchase requires a second click. A stage change updates the UI without silently changing the wallet action.

Normal draw rollover is accepted. Fresh pricing informs display/approval, but the app adds no execution-time draw or price lock. The deployed sale flags, positive pool, funds and number bounds still apply. Receipt events establish the actual purchased draw, unique tickets, attribution and amount paid. An old receipt cannot complete another account's order or reset an edited/new draft.

`transactions.ts` keeps compact versioned records for every supported order, including 100 tickets. A journal mutex serializes durable reservation and final wallet handoff. Wallet switches and send responses never hold a cross-flow lock. Previous pending or ambiguous attempts never block another deliberate action. Each explicit retry gets its own durable record; late responses remain observed after the initiating view is closed or retried. All journal writes use a separate shared mutex, prune resolved history before unresolved records, and preserve terminal outcomes, known hashes and wallet-selected nonces. Storage durability and wallet identity are checked before requesting a transaction. Restoration never repeats a wallet mutation. Hash-backed receipts reconcile automatically; lost-response purchase searches find bounded candidates for explicit verification. A missing hash, empty search or advanced nonce does not prove cancellation.

Claims refresh payout estimates without a quote-change gate. Ownership, chain, canonical calldata, contract identity and simulation remain mandatory. LP/vault actions retain their separate economic review rules. Direct contract-wallet wrapper execution is unsupported; EIP-7702 delegated EOAs retain the direct-transaction path. A wallet may instead execute the reviewed call as the account's own ERC-4337 operation through a canonical EntryPoint; only that operation's own outcome and logs count, and only Coinbase Smart Wallet call encodings are recognized.

Free ticket prize tiers are classified by matches (tiers 1 and 4), not by comparing a payout to exactly one dollar. They are ordinary USDC winnings claimable through Club. The official website's promotional guarantee excludes direct third-party purchases. No unsupported promotional entitlement is promised.

Win sharing creates a local branded PNG, offers Copy Image and native Share Image with verified award data and the account's referral link. X controls whether its composer retains both attachment and caption. Invite separately retains clipboard and browser sharing. No X credential or application backend is needed.

`contracts/` contains undeployed shared-vault implementations. `vaultDeployments.json` keeps activation disabled pending verified deployment evidence and independent acceptance. Native LP uses existing Megapot contracts. Footer and menu Support links open a DM draft to the configured Club X account. Provider capacity, live wallet pairing/signing, gateway behavior and live social crawlers require deployment-specific acceptance.

Wallet selection does not choose an operation's network. Read and simulation clients are configured for their target; the wallet adapter prepares that target inside the explicit Continue action, then checks account, provider and network immediately before handoff. No separate switch screen is required. Passive wallet reads have a twelve-second deadline; sends are never automatically retried.

Hashless purchases and claims recover through bounded indexed contract events plus exact transaction/receipt checks. Claim events are grouped by transaction before applying lookup limits. Every supported action can be retried deliberately after fresh checks, even while an earlier response is outstanding or has a hash. The original attempt remains in Activity. Recovery rotates bounded eligible work so old hashless approvals cannot starve new receipts. A different late wallet hash receives its own durable row without adopting another account or call. A hash already recorded for one attempt is never a recovery candidate for another, and explicit verification refuses it. Successful claim effects can mark other uncertain attempts superseded without inventing their transaction outcome.

Win cards are generated locally as PNG attachments with the canonical wordmark, amount, public URL and inviter QR. The current daily prize pool comes from the shell's fresh observation; unavailable pool amounts are omitted. The high-error-correction QR includes the Club icon and a four-module quiet zone. Native sharing and clipboard support are progressive enhancements. No dynamic social-card server or upload service is used.

The Invite reward example reads the current drawing and its expected jackpot tier from the deployed payout calculator at one block, then applies that drawing's referral win share. Stored settled payouts and the entire prize pool are not valid substitutes for an upcoming jackpot.
